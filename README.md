# شركة دادونيا للتجارة الدولية والنقل البحري
## منظومة إدارة العمليات وسجل الرقابة والتدقيق الأمني (Dadonia Trade & Audit Management System)

منظومة متكاملة لإدارة شركات الاستيراد والتصدير والتجارة الدولية، مصممة بالكامل وفق الهوية التحريرية والتجارية للشركات المصرية، مع واجهات عربية أصيلة تدعم اتجاه القراءة من اليمين إلى اليسار (RTL First)، ونظام رقابة وتدقيق صارم غير قابل للتعديل أو الحذف (Append-Only Audit Log) لحماية وتتبع حركة الموظفين والعمليات اللوجستية.

---

## المعمارية التقنية وحزم النظام (Apps)

بُنيت المنظومة باستخدام **Django 5 (Python 3.11 / 3.12)** وقوالب الخادم النقية (Server-Rendered Templates) مع تنسيقات CSS نقية بدون أي أطر عمل خارجية (No Tailwind, No Bootstrap)، وخط "Cairo" الرسمي.

### 1. تطبيق البيانات التجارية والعمليات (`core`)
- **دليل المنتجات (`Product`)**: اسم المنتج، التصنيف التجاري، المواصفات الفنية، بلد المنشأ، صورة المنتج، وحالة الجاهزية للتوريد.
- **سجل الشحنات والعمليات اللوجستية (`Shipment`)**: رقم بوليصة فريد (`reference`)، نوع العملية (استيراد / تصدير)، الصنف التجاري، دولة الميناء/المصدر، الكمية ومواصفة الحاوية، الحالة التشغيلية (قيد التجهيز / أبحرت / فحص وتخليص جمركي / تم التسليم)، وملاحظات الميناء.
- **طلبات الاستفسار والتوريد (`Inquiry`)**: اسم العميل/المؤسسة، رقم الهاتف والواتساب، البريد الإلكتروني، تفاصيل الطلب، علامة المتابعة والمعالجة، وتاريخ الاستلام.
- **الصفحات العامة**:
  - **الرئيسية (`/`)**: مؤشرات تشغيلية حية، حركة الشحنات النشطة، أبرز الحاصلات التصديرية، وتفاصيل المحطات البحرية بميناء الإسكندرية ودمياط والسخنة.
  - **دليل المنتجات والتصدير (`/products/`)**: تصفية حسب التصنيف، البحث النصي، والمواصفات الفنية وشروط التسليم (FOB/CIF).
  - **تتبع الشحنات والحاويات (`/track/`)**: استعلام حي برقم البوليصة مع مؤشر مرئي لمراحل الشحن والتخليص ونظام نافذة ACI.
  - **عن الشركة واللوجستيات (`/about/`)**: نبذة عن المؤسسة، معايير الجودة (GlobalGAP, ISO 22000, NFSA)، والمستودعات المبردة.
  - **طلب توريد وتواصل رسمي (`/contact/`)**: نموذج معتمد مدعوم بحقل صيد آلي (Honeypot Anti-Spam) وحماية ضد الإغراق بمعدل الإرسال (Rate Limiting per IP).

### 2. تطبيق الرقابة وتدقيق حركة الموظفين (`audit`) - الميزة الجوهرية
- **نموذج سجل النشاط (`ActivityLog`)**:
  - الموظف المسؤول (`user` - ForeignKey مع `SET_NULL`).
  - لقطة اسم المستخدم وقت الإجراء (`username_snapshot`) لضمان بقاء الأثر حتى لو حُذف الحساب.
  - نوع الإجراء: تسجيل دخول ناجح (`login`)، تسجيل خروج (`logout`)، محاولة فاشلة (`failed login`)، إنشاء سجل جديد (`create`)، تعديل بيانات (`update`)، وحذف سجل (`delete`).
  - بيان العملية والهدف (`target_description`).
  - تفاصيل التعديل (`changed_fields`): بنية JSON تسجل القيمة السابقة مقابل القيمة الجديدة (`{"اسم الحقل": {"old": "...", "new": "..."}}`).
  - عنوان بروتوكول الإنترنت (`ip_address`) وبيانات المتصفح والنظام (`user_agent`).
  - التوقيت الدقيق (`timestamp`).
- **آلية الرصد والالتقاط التلقائي**:
  - وسيط برمجي (`AuditUserMiddleware`) يلتقط هوية المستخدم وعنوان IP الحقيقي والمتصفح عبر `contextvars` غير المتزامنة والآمنة للخيوط (Thread-safe).
  - إشارات دجانغو (`Signals`) ترصد كافة عمليات تسجيل الدخول والخروج والإخفاق تلقائياً، وإشارات `pre_save` و `post_save` و `post_delete` تحسب الفروق الرقمية لكل العمليات على نماذج `core`.
- **حصانة السجل ضد التعديل أو الحذف (Strict Append-Only)**:
  - محمي برمجياً على مستوى النموذج (`save` و `delete` ترفع `PermissionError` فورياً إذا حاول أي كود تعديل أو حذف أي سجل).
  - محمي على مستوى الاستعلامات الجماعية (`QuerySet.delete()` و `QuerySet.update()` محظورة ومرفوضة).
  - محمي على مستوى لوحة تحكم دجانغو (`has_add_permission`، `has_change_permission`، و `has_delete_permission` ترجع `False` لجميع المستخدمين بما فيهم المالك والـ Superuser، مع إيقاف كافة خيارات الحذف الجماعي).
- **لوحة تحكم مالك المنظومة (`/activity/`)**:
  - وصول حصري ومحمي للمالك فقط (`is_superuser=True`، وتحويل أو رفض بقية المستخدمين برمز 403 Forbidden).
  - تصفية متقدمة حسب الموظف، نوع الإجراء، النطاق الزمني (من تاريخ / إلى تاريخ)، وبحث نصي حر.
  - تصدير السجل بصيغة **CSV مشفرة بـ UTF-8 BOM** لضمان فتح اللغة العربية بسلاسة تامة في برنامج Microsoft Excel بدون أي رموز غير مقروءة.
  - جدول إحصائي ملخص لكل موظف: موعد آخر دخول، عدد العمليات المنجزة اليوم، وعدد العمليات المنجزة خلال الأسبوع.

## الصلاحيات والأدوار الوظيفية

تم تكوين مجموعات العمل الإدارية المحددة في النظام:
1. **Sales (إدارة المبيعات والتجارة الخارجية)**: إدارة ومتابعة طلبات الاستفسار (`Inquiry`) وقراءة وتعديل الشحنات والاطلاع على المنتجات.
2. **Operations (إدارة العمليات واللوجستيات)**: إدارة الشحنات (`Shipment`) والمنتجات (`Product`) وقراءة الاستفسارات.
3. **Viewer (مراقب عام / تدقيق)**: صلاحيات قراءة واستعراض فقط (Read-only) لكافة البيانات التجارية دون إمكانية التعديل.
4. **Owner / Superuser (المالك)**: وصول كامل لكافة البيانات + صلاحية حصرية لدخول لوحة الرقابة وتدقيق حركة الموظفين (`/activity/`).

## الحسابات والصلاحيات

لا توجد حسابات أو كلمات مرور جاهزة في هذا المشروع. الحسابات الحقيقية تُنشأ يدوياً:

```bash
python manage.py createsuperuser   # حساب المالك (كلمة مرور 12 حرفاً على الأقل)
python manage.py setup_groups      # ينشئ مجموعات Sales / Operations / Viewer بدون مستخدمين
```

بعد ذلك أضف الموظفين من `/admin/` وضعهم في المجموعة المناسبة.

> **للتطوير المحلي فقط:** الأمر `python manage.py seed_demo` ينشئ حسابات تجريبية وبيانات عينة، ويرفض العمل
> عندما `DEBUG=False`. ولا يجوز تشغيله على الموقع الحي، ولا استخدام `--force` هناك.
> إن كانت قاعدة بيانات التطوير قد نُقلت يوماً إلى الإنتاج، عطّل حسابات الدمو أو غيّر كلمات مرورها قبل الإطلاق.

## التشغيل في البيئة المحلية (Local Setup)

### المتطلبات الأساسية
- Python 3.11 أو Python 3.12
- Node.js (لتشغيل خادم التطوير والوسيط على المنفذ 3000)

### 1. إعداد البيئة الافتراضية وتثبيت الحزم
```bash
python3 -m venv venv
source venv/bin/activate  # في بيئة Linux/macOS
# أو venv\Scripts\activate في بيئة Windows

pip install -r requirements.txt
```

### 2. إعداد المتغيرات البيئية
انسخ ملف الإعدادات النموذجية:
```bash
cp .env.example .env
```
يمكنك ضبط مفتاح الأمان وقاعدة البيانات في ملف `.env`.

### 3. تطبيق الهجرات وزرع البيانات التجريبية
```bash
python manage.py migrate
python manage.py seed_demo
python manage.py collectstatic --noinput
```

### 4. تشغيل الاختبارات الآلية
تحتوي المنظومة على **22 اختباراً آلياً شاملاً** تغطي التحقق من النماذج، وسائط الرقابة، كشف السبام، الحصانة ضد التعديل، وصلاحيات لوحة المالك:
```bash
python manage.py test
```

### 5. بدء تشغيل الخادم
لتشغيل دجانغو مباشرة:
```bash
python manage.py runserver 0.0.0.0:8000
```
أو عبر بيئة التطوير المدمجة:
```bash
npm run dev
```

## النشر في بيئة الإنتاج (Production Deployment)

### 1. إعداد خادم Gunicorn و WhiteNoise
المنظومة مهيأة ببرمجية **WhiteNoise** لضغط وتوزيع الملفات الثابتة بأعلى كفاءة بدون الحاجة لخوادم وسيطة معقدة للملفات الساكنة.

للتشغيل بواسطة Gunicorn:
```bash
gunicorn config.wsgi:application \
  --bind 0.0.0.0:8000 \
  --workers 3 \
  --threads 2 \
  --timeout 60 \
  --access-logfile - \
  --error-logfile -
```

### 2. إعداد Nginx كخادم وكيل عكسي (Reverse Proxy)
نموذج إعداد Nginx مع شهادة SSL والتوجيه إلى Gunicorn:
```nginx
server {
    listen 80;
    server_name dadonia-trade.eg www.dadonia-trade.eg;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name dadonia-trade.eg www.dadonia-trade.eg;

    ssl_certificate /etc/letsencrypt/live/dadonia-trade.eg/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/dadonia-trade.eg/privkey.pem;

    client_max_body_size 25M;

    # Static files handled via WhiteNoise or direct Nginx alias
    location /static/ {
        alias /app/applet/staticfiles/;
        expires 30d;
        add_header Cache-Control "public, no-transform";
    }

    location /media/ {
        alias /app/applet/media/;
        expires 7d;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### 3. التحول إلى PostgreSQL في بيئة الإنتاج
المنظومة مجهزة للاتصال بقاعدة بيانات PostgreSQL بمجرد تزويد المتغير البيئي في `.env` أو خادم السحابة:
```bash
DATABASE_URL=postgres://user:password@db-host:5432/dadonia_prod
# أو المتغيرات المنفصلة:
POSTGRES_DB=dadonia_prod
POSTGRES_USER=dadonia_admin
POSTGRES_PASSWORD=your_strong_password
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
```

## استراتيجية النسخ الاحتياطي لقاعدة البيانات وسجل الرقابة (Backup Strategy)

نظراً للأهمية القانونية والتشغيلية لسجل تدقيق الموظفين (`ActivityLog`)، يُوصى باتباع التدابير التالية:

1. **النسخ اليومي التلقائي لقاعدة البيانات (PostgreSQL Backup)**:
   جدولة أمر `pg_dump` يومياً عند الساعة 02:00 صباحاً عبر Cron Job مع رفع النسخة إلى تخزين سحابي معزول (S3 / GCS Bucket) مفعل عليه خاصية عدم التعديل (Object Lock / WORM):
   ```bash
   pg_dump -Fc -h $POSTGRES_HOST -U $POSTGRES_USER $POSTGRES_DB > /backups/dadonia_$(date +\%Y\%m\%d_\%H\%M).dump
   ```

2. **أرشفة سجلات النشاط (WAL Archiving)**:
   تفعيل خاصية Write-Ahead Logging (WAL) في PostgreSQL يتيح استرجاع قاعدة البيانات لأي ثانية محددة (Point-in-Time Recovery - PITR) في حال حدوث أي خطأ بشري أو كارثة فنية.

3. **النسخ الاحتياطي في بيئة SQLite الحالية**:
   في حال استخدام SQLite، يمكن عمل نسخة متطابقة بأمان بدون إيقاف الخدمة باستخدام أمر SQLite Online Backup:
   ```bash
   sqlite3 db.sqlite3 ".backup '/backups/db_backup_$(date +\%Y\%m\%d).sqlite3'"
   ```

## قرارات وإعدادات مقترحة لمالك الشركة

1. **اسم النطاق الرسمي والبريد التجاري**: تحديد الدومين الرسمي المعتمد (مثل `dadonia-trade.eg`) وإعداد خادم بريد SMTP لإرسال تنبيهات فورية بالبريد لمدير المبيعات عند تسجيل أي استفسار جديد.
2. **الصور الفوتوغرافية الحقيقية**: استبدال الرسوم التوضيحية النموذجية بصور حقيقية لمستودعات الشركة، محطة فرز الموالح، وبوابات الموانئ المصرية.
3. **حسابات الموظفين الفعلية**: تغيير كلمات مرور الحسابات التجريبية أو إنشاء حسابات موظفي المبيعات والعمليات الحقيقيين وإلحاقهم بالمجموعات المناسبة.

## الصفحات الداخلية وواجهة الـ API (تحديث)

الصفحات `/products` و`/about` و`/calendar` و`/contact` و`/track` أصبحت صفحات React حقيقية داخل الموقع (تنقّل فوري بدون إعادة تحميل، وتعمل الأزرار والقوائم من أي صفحة). البيانات الحيّة تأتي من Django عبر:

- `GET /api/products/?category=&q=` — دليل المنتجات
- `GET /api/track/?ref=` — تتبع الشحنة
- `POST /api/inquiry/` — طلب الاستفسار (نفس التحقق وحقل الصيد وحد المعدل لكل IP)

لعرض المنتجات والشحنات التجريبية شغّل مرة واحدة: `python3 manage.py migrate && python3 manage.py seed_demo`

## ملاحظات تشغيل مهمة (تحديث الباك إند)

- **الأمان افتراضياً**: `DEBUG` مغلق ما لم يُفعَّل صراحة. في الإنتاج لازم تحدد `SECRET_KEY` و`ALLOWED_HOSTS` في `.env` وإلا يرفض Django التشغيل. `npm run dev` يشغّل وضع التطوير تلقائياً بدون `.env`؛ أما `python manage.py test` و`runserver` المباشر فيحتاجان نسخة من `.env.example` (فيها `DEBUG=True`).
- **التشغيل في الإنتاج**: `npm run build` ثم `npm start`. الخادم يقدّم نسخة React المبنية، ويشغّل Django عبر gunicorn خلف بروكسي داخلي، ويطبّق الـ migrations تلقائياً قبل بدء الاستقبال. اجعل nginx أمام Express (`TRUST_PROXY=loopback`).
- **تنبيه الطلبات بالبريد**: ضع `INQUIRY_NOTIFY_EMAILS` وبيانات `EMAIL_*` ليصل فريق المبيعات إيميل فور وصول أي طلب جديد (زر الرد يرد على العميل مباشرة). بدون إعداد SMTP يُكتب البريد في سجل الخادم.
- **الحماية من الإغراق**: حد الإرسال محسوب على جدول الطلبات نفسه (5 طلبات / 15 دقيقة لكل IP)، وعنوان الـ IP يؤخذ من البروكسي الموثوق فقط فلا يمكن تزويره بهيدر `X-Forwarded-For`.
- **حسابات الدمو**: أمر `seed_demo` يعمل في وضع التطوير فقط ويرفض التنفيذ على الموقع الحي. أنشئ حساب المالك الحقيقي بـ `python manage.py createsuperuser`.
- **فحص الجاهزية**: `GET /api/health/` يتأكد من اتصال قاعدة البيانات.
